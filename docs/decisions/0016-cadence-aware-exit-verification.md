# ADR 0016: Cadence-aware verification of desktop pane exit

Status: accepted by user decision, 2026-11-09.

The desktop pane closes with a 100 ms opacity transition, retains its width during the fade and releases it on completion, with the existing 180 ms fallback. Real Electron runs on the qualified private X11 desktop delivered renderer animation-frame gaps of 134–172 ms during this interval. Consequently a strict requirement to observe two distinct intermediate opacity frames can fail even while a real transition starts. The earlier opacity-layer preparation candidate failed real tests and is not adopted.

The user explicitly authorized a narrower verification contract: retain the two-distinct-frame requirement when the renderer supplies adequate cadence; permit fewer samples only when recorded renderer starvation prevents them during the actual exit fade. The implementation defines sufficient evidence conservatively as an observer armed before the real click recording a gap covering at least half of the actual 100 ms fade and three median callback intervals measured from that same renderer after closure. The user did not prescribe those numerical thresholds. At least three post-close intervals are required for this calibration; if the actual start or cadence cannot be established, the test fails. Post-close samples establish ordinary callback cadence, while only the overlap of the gap with the actual fade qualifies for the exception. The observer must also establish an open baseline, a genuine running 100 ms opacity transition with the expected endpoints, held width and position, contained overflow, and a closed terminal state. Existing direction, width, inertness, focus and other assertions remain. A gap before the fade or after it does not qualify. Missing transition, incorrect duration, geometry or terminal state fails even during starvation. Negative tests enforce these boundaries.

This intentionally relinquishes the minimum two-observed-frame guarantee in the narrowly recorded starvation case. It does not prove physical presentation, cure the underlying scheduling stall, change product duration or fallback, or guarantee cadence on other platforms. Renderer observation itself may affect timing. The tests retain the normal-cadence requirement and do not synthesize frames, slow time or change the application to pass.
