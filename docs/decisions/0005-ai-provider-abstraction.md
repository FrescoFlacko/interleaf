# ADR 0005: AI Provider Abstraction & Authentication Model

## Status
Accepted

## Context & Problem Statement
Interleaf integrates conversational AI to assist with document comprehension, summarization, and query resolution. Users access AI models through two fundamentally different mechanisms: (1) subscription-backed local CLIs authenticated through existing browser/CLI logins (ChatGPT via Codex, Claude via Claude Code, Google via Antigravity), and (2) traditional API key providers (OpenRouter). Attempting to scrape web UIs or prompt users for passwords/cookies introduces severe security, privacy, and maintenance risks.

## Decision Drivers
- Support for subscription-authenticated local CLIs without handling user passwords or scraping session cookies.
- Support for API key providers (OpenRouter) with OS-backed secure credential encryption (`safeStorage`).
- Unified, pluggable `AIProvider` contract supporting real-time token streaming and cancellation.
- Deterministic, zero-cost offline testability via `FakeAIProvider`.

## Considered Options
1. **Option 1: Web Scraping & Cookie Extraction** — Prompt users for passwords or extract browser session cookies for ChatGPT/Claude web interfaces. (Rejected: Insecure, brittle, violates terms of service).
2. **Option 2: API Keys Only** — Force all users to purchase API credits via OpenAI/Anthropic/OpenRouter. (Rejected: Ignores users with active ChatGPT Plus/Pro or Claude subscriptions).
3. **Option 3: Hybrid Provider Abstraction** — Clean architectural separation between subscription-backed local CLIs and API key providers behind an `AIProvider` interface.

## Decision Outcome
Chosen **Option 3**.

### Architectural Invariants
1. **Subscription CLI Execution**:
   - Codex: When ChatGPT subscription status is connected, runs constrained non-interactive `codex exec` with `--json` streaming events for Reader Chat. Main resolves the canonical binary, creates a private empty app-owned cwd, passes the read-only sandbox and `approval_policy="never"`, ignores user config/rules, supplies a minimal allowlisted environment, bounds I/O and wall-clock time, supports cancellation, and aborts unsupported tool/events fail closed. The user explicitly authorized this residual-risk path. It is **not genuinely tool-free** because Codex 0.149.1 retains a built-in tool surface and exposes no tool-disable flag; no broader workspace or credential authority is granted.
   - Claude Code: Runs `claude` non-interactive print streaming using existing Claude subscription login; its configured tool-free invocation is the current subscription-backed Reader Chat path.
   - Antigravity: Runs `agy` using Google account authentication for Agent Mode. The current CLI adapter does not expose a verified tool-free Reader Chat path.
   - Pi: Runs `pi` 0.84.4 in its structured non-interactive JSON mode for Reader Chat whenever a main-owned probe reports a signed-in Pi model provider. Unlike Codex, this path **is** genuinely tool-free (`toolFreeMode=true`): `--no-tools` removes every built-in, extension and custom tool, and `--no-extensions --no-skills --no-prompt-templates --no-themes --no-context-files --no-session --no-approve` stop Pi discovering or trusting project- or user-owned material. The Reader AI prompt is installed with `--system-prompt` and the append slot is explicitly emptied (`--append-system-prompt ""`) so a discovered `APPEND_SYSTEM.md` cannot extend it. Main uses the same transport as the other CLIs: canonical binary, tokenized argv with `shell: false`, private empty app-owned cwd, minimal allowlisted environment, bounded I/O and wall-clock time, cancellation with process-tree termination, redacted diagnostics, and a fail-closed abort on tool use — a `tool_execution_*` or `toolcall_*` event, or a `toolResult` message, `toolUse` stop reason or `toolCall` content part inside an aggregate `AgentMessage` envelope — before its payload is rendered. Only assistant `text_delta` events become answer text; unknown or malformed structured output never does. The Reader AI prompt reaches Pi only as `--system-prompt`; the shared stdin body omits it and carries only the document context, history and question. Readiness is established without emitting a credential and without inference, from `--list-models` plus one bounded `pi auth check --provider <p> --json --no-refresh` per listed provider (never `--credentials`), and only models belonging to a provider that answered `ready` are exposed. The readiness probe fails closed: `ready` is concluded only from a clean exit 0, and the documented rejected verdict is parsed only for an ordinary exit 1 with no signal, kill, timeout or `maxBuffer` abort, and only to conclude *not* ready. `--offline` is included on every invocation: it suppresses Pi's startup, update, catalog and telemetry traffic and does **not** disable the selected remote model request.
   - Omp: Runs `omp` 18.1.16 (Pi's successor, same structured JSON event schema) in Reader Chat only — no Agent Mode execution profile is added. The invocation is genuinely tool-free in the same sense as Pi: `--mode json --print --no-tools --no-lsp --no-pty --no-extensions --no-skills --no-rules --no-session --no-title --approval-mode always-ask`, with the Reader AI prompt installed via `--system-prompt`, the append slot explicitly emptied (`--append-system-prompt ""`), a private empty app-owned `--cwd`, and a `--model` selector validated against Omp's own listing. Main uses the same transport as the other CLIs: canonical binary, tokenized argv with `shell: false`, minimal allowlisted environment, bounded I/O and wall-clock time, cancellation with process-tree termination, redacted diagnostics, and a fail-closed abort on tool use before its payload is rendered. Streaming requires a terminal `agent_end`/`turn_end`, so a truncated turn fails rather than being stored as a complete answer. **Omp has no `--offline` flag**, and none is claimed: the guarantee here is tool-free chat and no app-granted filesystem or tool execution, not network suppression. Detection and listing use `omp models --json --no-extensions` — no credential emitted, no model invoked — and the resulting catalog is untrusted: selectors are pattern-validated, names stripped of control characters, entries deduped and clamped, and the exposure capped at 128 models chosen round-robin across providers.
   - Local server (`local`): An HTTP provider for an inference server running on this machine — Ollama, or any OpenAI-compatible server (llama.cpp, LM Studio). One active endpoint profile is stored in existing settings (`ai.local`: mode, endpoint, selected model) with schema defaults, so no database migration is required; chat sessions already persist provider and model ids. Main owns validation, every network call and all persistence; the renderer uses only the existing typed `ai:get-provider-status` and `settings:update` channels. The renderer does hold and submit the endpoint text the user typed — it is a settings field — but that text is untrusted input, not a capability: it is validated and canonicalized exclusively in main, and the renderer holds no socket, no fetch and no way to reach the address it displays. The endpoint policy is validated and canonicalized once in main and is deliberately narrow: `http` only, a **literal** loopback authority (`127.0.0.1` or `[::1]`), no userinfo, path, query or fragment, and no names — `localhost` included — because a name is resolved and a resolver is the step a rebinding attack needs. Request paths (`/v1/models`, `/v1/chat/completions`, Ollama's read-only `/api/show`) are fixed app-owned constants appended to the canonical origin. The transport is `node:http` rather than `fetch` so that honouring no proxy, following no redirect and performing no name lookup are structural rather than optional; timeouts, byte/line bounds, cancellation and cleanup are enforced there. Only `choices[0].delta.content` becomes assistant text, terminal completion is required, reasoning fields are never exposed, and a tool or function call aborts the turn; no `tools`/`functions`/`tool_choice`/MCP field is ever sent. `toolFreeMode` is `true`, `hostedWebSearch` is `false`, and a forged `webSearch: true` is refused before a socket opens. Interleaf never downloads, pulls, starts, stops or deletes a model or runtime. **The claim is loopback-only connection, not on-device inference:** Ollama can route a cloud-capable model to its own infrastructure, which Interleaf cannot control or detect, so the UI states this and points at Ollama's own `OLLAMA_NO_CLOUD=1`.
   - Invariant: Interleaf NEVER prompts for user passwords or accesses browser cookies.
2. **API Key Management**:
   - OpenRouter keys are encrypted via Electron `safeStorage` (macOS Keychain-backed protection, Windows DPAPI, or Linux Secret Service when available).
   - Invariant: Plaintext is accepted only transiently from the secure input through a narrow validated `credentials.set` request. It is cleared after acknowledgement, never returned to the renderer or retained in renderer state, never stored in plaintext SQLite, and never written to logs.
3. **Offline CI Testing**: `FakeAIProvider` is registered for automated tests, ensuring zero API spend and 100% deterministic test execution.
4. **Optional Web Access — Provider-Hosted Only**:
   - Reader Chat is document-grounded by default. A user may opt one turn into a web search through an explicit composer control that defaults to off and returns to off after each send.
   - The only supported mechanism is a provider-hosted server tool: OpenRouter's beta web search (https://openrouter.ai/docs/guides/features/server-tools/web-search). Main adds `tools: [{ type: 'openrouter:web_search', parameters: { max_total_results: CHAT_WEB_SEARCH_MAX_TOTAL_RESULTS } }]` to that single request; the search runs on OpenRouter's servers and only its text result returns. Interleaf dispatches no tool call. The fixed `max_total_results` value bounds both per-turn cost and the volume of untrusted web text one turn can admit.
   - Invariant: local filesystem, shell, or general CLI tools are NEVER enabled to obtain web access. `capabilities.hostedWebSearch` is `false` for Claude Code, Codex, Antigravity, Pi, Omp, and the local server provider, because enabling a local CLI's tool surface would give untrusted document text a local execution path. Those providers keep the invocations described above; Pi in particular runs with `--no-tools` and `--offline`, so it has no search path to expose, the per-turn control is absent for it, and a forged `webSearch: true` is refused by the capability re-check below.
   - Invariant: the renderer never performs network access. It sends a validated boolean over typed IPC (`webSearch` on `chat:send-message`), and main re-checks it against the bound provider's own declared capability, rejecting a mismatch with a typed validation error rather than downgrading silently.
   - The composer presents only the explicit per-turn web-search control. It does not render an additional cost, processing, model-choice, or result-cap disclosure beside the control.
   - Invariant: provider search results are structured metadata, never message text. OpenRouter's `url_citation` annotations are parsed in main (absolute `http`/`https` only, bounded URL and title lengths, deduplicated, capped at `CHAT_WEB_SEARCH_MAX_TOTAL_RESULTS`) and reported as a typed `ChatWebSource[]` on the provider's `done` event, stored in their own `web_sources_json` column, and revalidated by schema at the shared boundary and again in the preload guard.
   - Invariant: provider metadata is excluded from model-authored history. `ChatMessage.content` is the model's own words and is the only field replayed to a model on later turns (history selection reads `content`; the provider maps it to `{ role: 'assistant', content }`). An untrusted webpage title placed in `content` would address the model as the assistant's own prior words on every subsequent turn, which escaping cannot prevent — so web sources are kept in a sibling field that nothing maps into history. A prompt-injection regression asserts a hostile title is absent from the outgoing request after being streamed, stored, reloaded, and rebuilt into context.
   - Web results stay distinguishable from document provenance: `[src-N]` chips are still validated against the exact envelope sent, while web sources render from typed metadata under their own heading as inert, non-navigable elements showing the provider's title as literal text beside the validated host.

## Consequences
- **Positive**: Users leverage their existing ChatGPT/Claude/Google subscriptions seamlessly.
- **Positive**: API keys are securely protected at rest using OS hardware/keychain facilities.
- **Negative**: CLI subscription features depend on the user having the respective CLI installed and authenticated on their workstation.
- **Negative**: Web search is available only on the API key provider, so a subscription-CLI user cannot reach the web from Reader Chat at all. That asymmetry is deliberate: the alternative is a local tool surface driven by untrusted document text.
